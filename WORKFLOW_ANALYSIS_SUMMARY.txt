VALIDATION SYSTEM ANALYSIS
================================================================================

EXISTING VALIDATION (Backend):

Severity Levels:
  - ERROR: Blocks execution (8 types)
  - WARNING: Shows warning but allows execution (6 types)
  - INFO: Informational only (2 types)

Current Checks (10 validators):
  1. Empty workflow detection
  2. Circular dependency detection (DFS algorithm)
  3. Dead node detection (BFS algorithm)
  4. Required field validation per node type
  5. Edge source/target validation
  6. Self-loop detection
  7. Start node validation (must exist)
  8. End node validation
  9. Node compatibility checks (e.g., condition nodes)
  10. Isolated node detection
  11. Variable reference validation (regex pattern matching)

EXISTING VALIDATION (Frontend):
  1. Disconnected node detection
  2. Cycle detection (DFS)
  3. Start node existence
  4. End node existence
  5. Multi-start point detection

VALIDATION GAPS IDENTIFIED:
  1. No node-specific schema validation (configs are flexibly typed)
  2. No type compatibility checking for variable references
  3. No resource limit validation (node count, edge count, payload size)
  4. Templates not validated on load (security/integrity gap)
  5. Advanced node patterns not fully validated (split/merge)
  6. Retry policies not validated
  7. No URL/endpoint validation (security gap)
  8. No payload size limits

NODE TYPES REFERENCE
================================================================================

Node types follow a pattern:
  "type": "node-type-name"

Config Structure:
  "config": {
    // Required fields depend on node type
    // Can use variable interpolation: {{var_name}} or ${var_name}
    "field1": "value",
    "field2": 123,
    "field3": "{{other_node_output}}"
  }

REQUIRED CONFIGS BY NODE TYPE (from validator):
  "http":       ["url", "method"]
  "email":      ["to", "subject"]
  "database":   ["connection", "query"]
  "transform":  ["expression"]
  "condition":  ["condition"]
  "loop":       ["items"]
  "delay":      ["duration"]
  "webhook":    ["url"]
  "llm":        ["prompt"]
  "code":       ["code"]

VALID START NODE TYPES:
  trigger, manual, schedule, webhook_trigger, http

VALID END NODE TYPES:
  http, email, database, webhook, transform, output, success, error

VARIABLE INTERPOLATION SYNTAX:
  ${variable_name}     - For simple references
  {{expression}}       - For template expressions
  {{outputs.node-id}}  - For node output references

================================================================================
WORKFLOW EXECUTION FLOW
================================================================================

1. Frontend Validation (Real-time as user builds)
   - workflow-validation.tsx validates structure
   - Shows errors/warnings in UI
   - Non-blocking, advisory only

2. User Submits Workflow
   - POST /workflows/{id}/execute
   - Optional: async_execution flag
   - Optional: inputs for variables

3. Backend Route Handler
   - Loads workflow from database
   - Checks status is active/draft
   - Creates WorkflowRun record
   - Currently: Does NOT call validator explicitly (gap)

4. Backend Validation (SHOULD be added)
   - Call workflow_validator.validate_workflow()
   - If errors found: Return 400 Bad Request
   - If valid: Continue to execution

5. Workflow Executor
   - Initializes execution context
   - Builds execution queue from node dependencies
   - Processes nodes sequentially (or in parallel for split nodes)
   - Updates node_states as execution progresses
   - Broadcasts WebSocket updates to frontend
   - Collects logs and errors
   - Saves final WorkflowRun record

6. Result Tracking
   - Frontend polls or uses WebSocket to get updates
   - ExecutionStatusResponse contains all details
   - Results stored in WorkflowRun document

KEY INSIGHTS
================================================================================

1. ARCHITECTURAL PATTERNS:
   - Flexible node configs (Record<string, unknown>) allow extensibility
   - MongoDB + Beanie for backend, React Flow for frontend
   - WebSocket for real-time execution updates
   - Separate frontend and backend validation logic

2. VALIDATION MATURITY:
   - Good: Graph validation (cycles, reachability) already implemented
   - Gap: No node-specific schema validation
   - Gap: No integration of backend validation in execution flow
   - Gap: No security validation (URLs, payloads)

3. SCALABILITY NOTES:
   - All validation checks are O(V+E) complexity
   - Suitable for workflows up to thousands of nodes
   - No explicit resource limits yet

4. EXTENSIBILITY:
   - Easy to add new node types (just add to component-library)
   - Easy to add new validation rules (add methods to WorkflowValidator)
   - Easy to add new required fields (extend REQUIRED_CONFIGS)

5. INTEGRATION POINTS:
   - Frontend validation is real-time and advisory
   - Backend validation should be mandatory before execution
   - No API endpoint currently exposes validation results
